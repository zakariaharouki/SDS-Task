# Scheme Pipeline Tracker: Design

A small app for a housing developer to track the schemes in their pipeline:
add, edit and list schemes, filter and sort by status, see per-scheme figures
(total homes, % affordable, total value) and a portfolio summary.

Guiding rule from the brief: *keep it small and finish it.* Anything not needed
for the three required features is listed under "Deliberately left out".

---

## 1. Stack and hosting

| Layer    | Choice                                   | Hosted on            |
|----------|------------------------------------------|----------------------|
| API      | .NET 8 Web API (C#), controllers         | Render (Docker)      |
| Frontend | React + **TypeScript**, Vite             | Vercel               |
| Database | MongoDB (official C# driver)             | MongoDB Atlas (M0)   |
| Tests    | xUnit, Testcontainers (MongoDB), Vitest, React Testing Library | GitHub Actions |

**TypeScript, not plain JS.**
Reason: the brief says their front ends are "React with TypeScript". Typed API
contracts also catch shape mismatches between the API and the UI at compile time.

## 2. Data model

### 2.1 Scheme

| Field         | Type                 | Notes                                             |
|---------------|----------------------|---------------------------------------------------|
| `id`          | string (ObjectId)    | Generated by MongoDB                              |
| `name`        | string               | Required, trimmed, 1–200 chars                    |
| `siteAddress` | string               | Required, trimmed, 1–300 chars. Single free-text field |
| `status`      | enum (string)        | `Appraisal`, `Planning`, `OnSite`, `Complete`     |
| `tenureMix`   | TenureMix            | Fixed object, see below                           |
| `version`     | int                  | Optimistic concurrency, starts at 1 (see 5.4)     |
| `createdAt`   | DateTime (UTC)       | Set by server on create, never by client          |
| `updatedAt`   | DateTime (UTC)       | Set by server on every write                      |

**Address is one text field, not street / town / postcode.**
Reason: nothing in the brief filters, validates or geocodes by address part.
Trade-off: no postcode search or validation later without a migration.

### 2.2 TenureMix

A fixed object with 4 named properties, **not an array**:

```json
"tenureMix": {
  "socialRent":      { "homes": 40, "averageValue": 150000.00 },
  "affordableRent":  { "homes": 30, "averageValue": 180000.00 },
  "sharedOwnership": { "homes": 20, "averageValue": 220000.00 },
  "marketSale":      { "homes": 60, "averageValue": 350000.00 }
}
```

Each tenure line: `homes` (int) and `averageValue` (decimal, GBP).

Reason: the brief defines exactly four tenures. A fixed shape makes "missing" or
"duplicate" tenures impossible, so there is less to validate.
Trade-off: adding a new tenure needs a code change. Acceptable, because new
tenure types are rare and come with policy change anyway.

### 2.3 Money

- `decimal` in C#, stored as `Decimal128` in MongoDB (`[BsonRepresentation(BsonType.Decimal128)]`).
  Never `double`, because floating-point errors in money totals are a classic bug.
- Max 2 decimal places (pence) on input.
- **The frontend never calculates money.** All totals come from the API; the UI
  only formats them (`Intl.NumberFormat('en-GB', { style: 'currency', currency: 'GBP' })`).
  Reason: JavaScript numbers are doubles, so the same bug would come back in the browser.
- Largest possible scheme value: 4 tenures × 10,000 homes × £10,000,000 = £4×10¹¹,
  well inside `decimal` range and exact in JSON numbers at this size.

### 2.4 Status

`Appraisal → Planning → OnSite → Complete`

- Stored as a string in Mongo (`"OnSite"`), not a number, so the data is readable
  and reordering the enum can't corrupt it.
- Serialized as the same string in JSON (`SchemeStatusJsonConverter`). It accepts only
  the exact name; the built-in converter also accepts numbers and ignores case.
- Sorting by status uses **pipeline order**, not alphabetical (alphabetical would
  put Complete before Planning). Implemented in the Mongo query with
  `$indexOfArray(["Appraisal","Planning","OnSite","Complete"], "$status")`.
  The order list lives in one place in C# and is passed into the query.
- **Any status change is allowed, including going backwards.**
  Reason: real schemes do move back (planning refused → back to appraisal).
  Enforcing a workflow would be a guess at business rules I don't know.

### 2.5 Computed figures

Defined once, in a pure C# class (`SchemeCalculator`) with no I/O, so it is the
easiest thing to unit test:

| Figure               | Formula                                                        |
|----------------------|----------------------------------------------------------------|
| `totalHomes`         | sum of `homes` across all 4 tenures                            |
| `affordableHomes`    | `socialRent + affordableRent + sharedOwnership` homes          |
| `affordablePercent`  | `affordableHomes / totalHomes × 100`, rounded to 1 dp with midpoints away from zero (0.25 → 0.3); **`null` when `totalHomes = 0`** (UI shows "n/a") |
| `totalValue`         | sum of `homes × averageValue` across all 4 tenures             |

- **Affordable = social rent + affordable rent + shared ownership**, exactly as the
  brief defines it. Market sale is the only non-affordable tenure.
- **0 homes → `null` in the API, shown as "n/a" in the UI, never 0%.** Reason: an
  appraisal-stage scheme with no mix yet is "unknown", not "0% affordable". Showing
  0% would wrongly flag it as a scheme with no affordable housing. Because of the
  rule in section 3 (at least 1 home once past Appraisal), only Appraisal schemes
  can show "n/a".
- The API returns `null` rather than the string "n/a", so the field stays a number
  type; the UI's `Percent` component turns `null` into "n/a". Same for the portfolio
  summary when the whole portfolio has 0 homes.
- Rounding only at the end (percentage to 1 dp for display); `totalValue` is exact.
- Portfolio `affordablePercent` is calculated from portfolio totals
  (`Σ affordable / Σ total`), **not** the average of each scheme's percentage.
  Averaging percentages would let a 10-home scheme weigh as much as a 500-home one.

**Computed figures are stored on the document on every write** (`totals` sub-object)
as well as returned in responses.
Reason: sorting by `totalHomes` / `totalValue` and building the summary then become
plain indexed Mongo queries, and the formula lives only in C# (one source of truth),
not duplicated into an aggregation pipeline.
Trade-off: the stored totals could drift if someone edits Mongo by hand. Mitigation:
the API is the only writer, and `SchemeService` always recalculates before saving.

### 2.6 Mongo document (stored shape)

```json
{
  "_id": ObjectId("..."),
  "name": "Riverside Phase 2",
  "siteAddress": "Unit 4, Riverside Road, Leeds LS1 4AB",
  "status": "Planning",
  "tenureMix": { ... as above ... },
  "totals": { "totalHomes": 150, "affordableHomes": 90, "totalValue": Decimal128("36800000.00") },
  "duplicateKey": "riverside phase 2|unit 4, riverside road, leeds ls1 4ab",
  "version": 3,
  "createdAt": ISODate("2026-11-02T10:00:00Z"),
  "updatedAt": ISODate("2026-11-03T09:12:00Z")
}
```

API DTOs are separate classes from the Mongo document, so the stored shape can
change without breaking the API contract.

### 2.7 Indexes

- `status`
- `name` with case-insensitive collation (`en`, strength 2), so "alpha" and "Beta" sort naturally
- `totals.totalHomes`, `totals.totalValue`
- **`duplicateKey` — unique.** Enforces the duplicate rule in section 3

The sort indexes are mostly for correctness and to show intent on a small dataset.
The unique index is load-bearing: it is what actually blocks duplicates.

## 3. Validation rules

The **API is the source of truth**. The frontend repeats the same rules for fast
feedback, but never relies on them.

| Field                      | Rule                                                                 |
|----------------------------|----------------------------------------------------------------------|
| `name`                     | Required. Trimmed first. 1–200 chars after trim. Whitespace-only = missing |
| `siteAddress`              | Required. Trimmed first. 1–300 chars after trim                      |
| `status`                   | Required. Must be one of the 4 values (case-sensitive, exact string) |
| `tenureMix`                | Required. All 4 tenures required (missing tenure = 400, not "assume 0") |
| `homes` (each)             | Whole number, 0–10,000. Decimals like `2.5` rejected, not rounded    |
| `averageValue` (each)      | 0–10,000,000, max 2 decimal places                                   |
| `averageValue` vs `homes`  | `averageValue` must be > 0 if `homes` > 0                             |
| `homes` = 0 (one tenure)   | Allowed; `averageValue` is stored as given but contributes £0         |
| Total homes vs `status`    | **Total homes must be ≥ 1 when status is `Planning`, `OnSite` or `Complete`.** 0 total homes is only allowed at `Appraisal` |
| `name` + `siteAddress`     | **Must not match another scheme** (see duplicate rule below). 409 if it does |
| `version` (PUT only)       | Required; must match the stored version (see 5.4)                    |
| `id`, `createdAt`, `updatedAt`, totals | Rejected with a 400 if sent by the client; always set by the server |

Extra decisions:

- **0 total homes is allowed only at Appraisal; from Planning onwards at least 1
  home is required.** Reason: early appraisal schemes often have no agreed mix yet,
  and blocking them would push users to enter fake numbers. A scheme that has gone
  into planning, is on site or is complete must have homes, so 0 there is a data
  entry mistake.
  - Checked on every create and update, against the status being saved. Moving a
    0-home scheme from Appraisal to Planning fails until homes are added; moving a
    scheme back to Appraisal is always fine.
  - Error key is `tenureMix`, message: "A scheme in Planning, On site or Complete
    must have at least 1 home."
  - Trade-off: a user who wants to record "planning submitted, mix not final" has
    to enter an estimate. Acceptable, as planning applications state a mix.
- **Duplicate schemes are blocked: no two schemes may have the same name *and* the
  same site address.** Same name at a different address is fine (phases, or common
  names like "The Old Depot"), and so is a different name at the same address
  (Phase 1 and Phase 2 on one site).
  - "Same" means after normalising: trim, collapse repeated spaces to one, and
    compare case-insensitively. So `"Riverside  Phase 2"` and `"riverside phase 2"`
    match. Punctuation is not normalised (`"Rd"` vs `"Road"` are different); fuzzy
    address matching would be a guess and could block real schemes.
  - Enforced by a **unique index** on a stored `duplicateKey` field
    (`normalisedName|normalisedAddress`), recalculated on every write. Reason: a
    "check, then insert" in code has a race (two saves at once both pass the check);
    the unique index can't be beaten. The repository catches Mongo's duplicate key
    error (code 11000) and turns it into a 409.
  - Known limit: a `|` in a name or address can make two different schemes share a
    key (`A|B` at `C` and `A` at `B|C`), which gives a false 409. Accepted: it needs a
    `|` and otherwise identical wording, and rewording gets past it. Escaping isn't
    worth the extra code for such a rare case.
  - On PUT, the scheme can keep its own name and address; the index only clashes
    with *other* documents.
  - Response: **409 Conflict** Problem Details with field errors on `name` and
    `siteAddress`: "A scheme with this name already exists at this address."
    409 rather than 400 because the input is valid on its own; it conflicts with
    existing data.
  - Trade-off: the duplicate key duplicates name/address data in the document.
    Fine: it's set only by `SchemeService`.
- **Missing tenure is an error, not 0.** Reason: silent defaults hide client bugs.
- **Unknown JSON properties are rejected** (`JsonUnmappedMemberHandling.Disallow`),
  so a typo like `affordbleRent` fails loudly instead of being dropped.
- Implemented with **FluentValidation** (rules are plain classes, easy to unit test,
  and the cross-field `averageValue`/`homes` rule is natural to express).

### 3.1 Error format

All errors use RFC 7807 Problem Details (`application/problem+json`). Validation
errors return **400** with field paths the frontend can map straight to inputs:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "name": ["Name is required."],
    "tenureMix.marketSale.averageValue": ["Average value must be greater than £0 when there are homes."]
  }
}
```

- JSON that can't be parsed into the model (e.g. `"homes": 2.5`, `"status": "Done"`)
  also returns a 400 with a **friendly message**, not the raw serializer exception.
- Messages are written for the user ("Homes must be a whole number"), not for the
  developer ("Could not convert System.Decimal to System.Int32").
- Unhandled errors return a generic 500 Problem Details with a trace id. No stack
  traces outside Development.

## 4. API

Base path: `/api`. JSON, camelCase. OpenAPI/Swagger UI at `/swagger` (useful for
testers and for the walkthrough).

| Method | Path                     | Purpose                                  | Success |
|--------|--------------------------|------------------------------------------|---------|
| GET    | `/api/schemes`           | List, filter, sort                       | 200     |
| GET    | `/api/schemes/{id}`      | One scheme with computed figures         | 200     |
| POST   | `/api/schemes`           | Create                                   | 201 + `Location` header |
| PUT    | `/api/schemes/{id}`      | Full update                              | 200     |
| GET    | `/api/schemes/summary`   | Portfolio summary                        | 200     |
| GET    | `/health`                | Liveness for Render + cold-start check   | 200     |

### 4.1 GET /api/schemes

Query parameters:

| Param     | Values                                                    | Default  |
|-----------|-----------------------------------------------------------|----------|
| `status`  | one or more, repeatable: `?status=Planning&status=OnSite` | all      |
| `sortBy`  | `status`, `name`, `totalHomes`, `totalValue`, `updatedAt` | `status` |
| `sortDir` | `asc`, `desc`                                             | `asc`    |

- Invalid `status` / `sortBy` / `sortDir` → 400 (not silently ignored). Values are
  exact and case-sensitive, so `?status=planning` and `?status=1` are rejected.
- **Stable sort:** every sort has tie-breakers `name asc`, then `_id`, so rows with
  equal values don't jump around between requests.
- Each list item includes the computed figures, so the list can show them without
  N extra calls.
- **No pagination.** Reason: a developer's pipeline is tens of schemes, not
  thousands. Trade-off noted in "Deliberately left out"; adding `page`/`pageSize`
  later is backwards compatible.

Response item:

```json
{
  "id": "6725f0...",
  "name": "Riverside Phase 2",
  "siteAddress": "Unit 4, Riverside Road, Leeds LS1 4AB",
  "status": "Planning",
  "tenureMix": { ... },
  "totalHomes": 150,
  "affordableHomes": 90,
  "affordablePercent": 60.0,
  "totalValue": 36800000.00,
  "version": 3,
  "createdAt": "2026-11-02T10:00:00Z",
  "updatedAt": "2026-11-03T09:12:00Z"
}
```

### 4.2 GET /api/schemes/{id}

- Returns the shape above.
- Unknown id **or** malformed id (not a valid ObjectId) → **404**.
  Reason: the caller can't do anything different with "malformed" vs "missing", and
  404 avoids leaking id format details.

### 4.3 POST /api/schemes

- Body: `name`, `siteAddress`, `status`, `tenureMix`.
- Returns 201, the created scheme, and `Location: /api/schemes/{id}`.
- 400 for validation errors (including 0 homes past Appraisal); 409 for a duplicate
  name + address.

### 4.4 PUT /api/schemes/{id}

- **Full replacement** of editable fields (`name`, `siteAddress`, `status`,
  `tenureMix`) plus `version`. All required. No PATCH.
  Reason: the edit form always sends the whole scheme, so PUT is simpler and has
  no "which fields were sent" ambiguity.
- 404 if not found; 400 for validation errors; 409 if `version` doesn't match
  (see 5.4) or if the new name + address duplicates another scheme. The two 409s
  have different `title`s and messages so the UI can tell them apart.
- `createdAt` is preserved; `updatedAt` and `version` are set by the server.

### 4.5 GET /api/schemes/summary

```json
{
  "schemeCount": 12,
  "totalHomes": 1840,
  "affordableHomes": 760,
  "affordablePercent": 41.3,
  "totalValue": 512300000.00,
  "byStatus": [
    { "status": "Appraisal", "schemeCount": 3, "totalHomes": 400, "affordableHomes": 180, "totalValue": 90000000.00 },
    { "status": "Planning",  "schemeCount": 4, "...": "..." },
    { "status": "OnSite",    "schemeCount": 3, "...": "..." },
    { "status": "Complete",  "schemeCount": 2, "...": "..." }
  ]
}
```

- Required by the brief: total homes, total affordable homes, total value. The rest
  is cheap and useful.
- `byStatus` always contains all 4 statuses in pipeline order, with zeros for empty
  ones, so the UI doesn't have to fill gaps.
- Accepts the same optional `status` filter as the list, so the summary can match
  what the user is looking at.
- Empty database → all zeros, `affordablePercent: null` (UI shows "n/a"), never a 500.
  Same for any `byStatus` row with 0 homes.
- Route `/summary` is registered so it can't be captured by `/{id}`
  (explicit route constraint / ordering, covered by a test).

## 5. Backend structure

```
backend/
  SchemeTracker.sln
  SchemeTracker.Api/
    Controllers/    HTTP only: routes, status codes
    Dtos/           Request and response shapes (the API contract)
    Exceptions/     Conflicts with existing data, returned as 409
    Interfaces/     ISchemeService, ISchemeRepository
    Mapping/        DTO ↔ model copying, no business rules
    Models/         Scheme, TenureMix, TenureLine, SchemeTotals, SchemeStatus,
                    SchemeStatusTotals, with MongoDB mapping attributes
    Options/        MongoOptions
    Repositories/   SchemeRepository
    Services/       SchemeService
    Validation/     Validators, request error responses
    Program.cs      Service registration, pipeline
  SchemeTracker.Tests/   Unit and integration tests, one project
  Dockerfile
```

`SchemeCalculator` and `SchemeDuplicateKey` are in `Services/`. The `Dockerfile` is
planned but not added yet.

### 5.1 Layers

Requests flow **Controller → Service → Repository → MongoDB**, in one API project.
Each layer depends on the next through an interface.

- **Controllers** are thin: HTTP only, no business rules.
- **Services** hold the application flow: validate → apply rules → call repository →
  map to DTO. `SchemeService` recalculates `totals` and `duplicateKey` before every
  save. Trade-off: every code path that saves a scheme must go through the service,
  because the repository stores what it is given.
- **Repositories** are the only code that queries MongoDB.
- **Mapping** only copies data. It takes the affordable percentage as an input, so
  the formula stays in `SchemeCalculator`.
- `SchemeCalculator` stays pure, with no I/O, so it remains the easiest thing to test.

Reason: clear separation of responsibilities, and each layer can be tested on its own.
Trade-off: more classes than one entity and five endpoints strictly need, and because
models carry MongoDB attributes, they are not free of the database driver.

### 5.2 Configuration and secrets

- `Mongo__ConnectionString`, `Mongo__Database`, `Cors__AllowedOrigins` from
  environment variables (Render dashboard). Never committed.
- The API refuses to start if the Mongo settings are missing, so a bad deploy fails
  immediately rather than on the first request.
- `appsettings.Development.json` points at a local Docker Mongo and has no credentials.
- `.env` holds local values. It is ignored by git, and a pre-push hook
  (`.githooks/pre-push`) blocks any push whose commits contain it, including after
  `git add -f`. Each clone enables the hook once with
  `git config core.hooksPath .githooks`.
  Trade-off: `git push --no-verify` can still bypass a local hook.
- `.env.example` documents every variable with no real values.
- **CI receives no database credentials.** Tests pin their own settings or use
  Testcontainers, so they can never reach a real database.

### 5.3 CORS

- Only the Vercel production URL (and `http://localhost:5173` in Development) are
  allowed. Not `AllowAnyOrigin`, and a `*` in the setting is ignored.
- `Cors__AllowedOrigins` is a comma-separated list. If it's empty, the API still starts
  but allows no browser origins, so the API can be deployed before the Vercel URL exists.
- Vercel preview URLs change per deploy; allow them by a configured pattern or not
  at all (decision: production URL only, keep it simple).

### 5.4 Concurrency

Optimistic concurrency with `version`:

- PUT updates with filter `{ _id: id, version: clientVersion }` and `$inc` version.
- If no document matched but the id exists → **409 Conflict** with a message like
  "This scheme was changed by someone else. Reload to see the latest version."

Reason: two people editing the same scheme would otherwise silently overwrite each
other (last write wins). Cheap to add, and a good "what would break" answer.

### 5.5 Time

- All timestamps UTC (`DateTime.UtcNow` via an injected `TimeProvider`, so tests can
  control time). The UI converts to local time for display.
- Timestamps are set to whole milliseconds, because that's all MongoDB stores, so a
  create response matches the same scheme when it is read back.

## 6. Frontend

```
frontend/
  src/
    api/          Typed client (fetch wrapper), DTO types, error parsing
    features/schemes/
      SchemeListPage.tsx      Table + status filter + sort controls + summary cards
      SchemeFormPage.tsx      Create and edit (same form)
      SchemeDetail.tsx        Figures + optional tenure chart
      validation.ts           Same rules as the API, for instant feedback
    components/   Money, Percent, StatusBadge, ErrorBanner, LoadingState
    lib/format.ts GBP / percent / date formatting
```

- **Vite + React + TypeScript**, React Router for `/`, `/schemes/new`, `/schemes/:id/edit`.
- **TanStack Query** for fetching/caching; after create/edit, the list and summary
  queries are invalidated so totals refresh.
- **react-hook-form** for the form. Server 400 errors are mapped onto fields by
  their `errors` keys (e.g. `tenureMix.marketSale.averageValue`).
- **Filter and sort state live in the URL** (`/?status=Planning&sortBy=totalValue&sortDir=desc`).
  Reason: survives reload, back button works, and a tester can share a link.
- Tenure mix is shown as a fixed 4-row table in the form (tenure, homes, average
  value, line value), matching the fixed object in the API.
- Line values and totals shown in the form while typing are labelled as a
  **preview**; the saved figures always come from the API.
- States handled on every screen: loading, empty ("No schemes yet. Add your first
  one"), error (with retry), and the two kinds of 409: version conflict (reload
  prompt) and duplicate scheme (error shown on the name and address fields).
- `null` percentages render as "n/a" everywhere (list, detail, summary), via one
  shared `Percent` component, so there is one place to test it.
- The form warns as soon as status is set past Appraisal with 0 total homes, before
  submit. The API still enforces it.
- **Cold start:** Render free tier sleeps after ~15 minutes idle and can take
  30–60 s to wake. The UI shows "Waking up the server…" after a few seconds of
  loading instead of looking broken.
- Accessibility basics: real `<label>`s, errors linked with `aria-describedby`,
  table with proper headers, sort buttons announce direction, keyboard usable.
- Optional extra (only if time): stacked bar chart of tenure mix per scheme (Recharts).

## 7. Testing

Focus on the logic that matters, as the brief asks.

### 7.1 Unit tests (xUnit), highest value

`SchemeCalculator`:
- totals for a normal mix
- affordable = social + affordable rent + shared ownership; market sale excluded
- 0 total homes → `affordablePercent` is `null`, not 0 and not divide-by-zero
- 100% affordable and 0% affordable
- money exactness: e.g. 3 × £0.10 sums to exactly £0.30 (would fail with double)
- maximum values don't overflow
- percent rounding (e.g. 1/3 → 33.3)
- portfolio % is weighted by homes, not an average of scheme percentages

Validators:
- name/address: empty, whitespace-only, trimmed, exactly 200/300, 201/301
- homes: negative, 10,001, 0
- averageValue: > 0 required when homes > 0; 0 allowed when homes = 0; > 10M rejected; 3 dp rejected
- invalid status
- 0 total homes: valid at Appraisal; invalid at Planning, OnSite and Complete
- 1 home at Planning is valid (boundary)

Duplicate key normalisation: trim, collapsed spaces and case differences produce the
same key; `"Rd"` vs `"Road"` produce different keys.

Status ordering: pipeline order, not alphabetical.

### 7.2 API integration tests (WebApplicationFactory + Testcontainers MongoDB)

Real Mongo in Docker, so `Decimal128` mapping, collation and sorting are actually tested.

The tests use `mongo:7.0`, because 8.0 and newer refuse to start on Linux kernels 6.19
to 7.0.13, which CI runners currently use. Trade-off: the tests run on an older major
version than Atlas may use. Move up once runners reach kernel 7.0.14.

- POST valid → 201 + Location; GET by id returns same data with figures
- POST invalid → 400 with expected field keys
- `"homes": 2.5`, unknown status, unknown property → 400 friendly message
- GET unknown / malformed id → 404
- PUT updates `updatedAt`, keeps `createdAt`, bumps `version`
- PUT with stale version → 409
- POST a second scheme with the same name + address (different case/spacing) → 409
  with errors on `name` and `siteAddress`
- same name at a different address → 201; PUT a scheme without changing its own
  name/address → 200 (doesn't clash with itself)
- PUT that renames a scheme onto another scheme's name + address → 409
- two concurrent POSTs of the same duplicate → exactly one 201, one 409 (proves the
  unique index, not just the code check)
- PUT moving a 0-home scheme from Appraisal to Planning → 400; moving back to
  Appraisal → 200
- list filtered by multiple statuses; sort by status uses pipeline order; desc works
- summary on empty DB → zeros and null %; summary matches sum of schemes
- `/api/schemes/summary` is not treated as an id
- a value like £123,456.78 round-trips through Mongo exactly

### 7.3 Frontend tests (Vitest + React Testing Library)

- form shows field errors from client rules and from a mocked 400 response
- money/percent formatting (`£1,234,567.00`, "n/a" for null)
- duplicate 409 shows the message on the name and address fields
- changing filter/sort updates the URL and the request

### 7.4 CI

GitHub Actions: build + test API (Docker available for Testcontainers) and build +
test frontend on every push. No database credentials or other secrets are passed to
CI (see 5.2). Badge in README.

## 8. Deployment

| Piece    | Where           | Notes |
|----------|-----------------|-------|
| API      | Render Web Service, Docker | Render has no native .NET runtime, so a multi-stage Dockerfile (`sdk` → `aspnet`). Listen on `$PORT`. Health check `/health` |
| Frontend | Vercel          | `VITE_API_BASE_URL` env var; SPA rewrite of all routes to `index.html` (`vercel.json`) so deep links work |
| Database | MongoDB Atlas M0 | Separate DB user with readWrite on this database only |

- **Atlas network access is `0.0.0.0/0`.** Reason: Render's free tier has no static
  outbound IPs. Trade-off: security relies on the strong DB password + TLS only.
  With a paid tier, I'd restrict to Render's static IPs.
- Indexes created at startup (idempotent `CreateMany`). If that fails, the API stops,
  because the unique index is what blocks duplicates. So the API needs a reachable
  MongoDB to start, including in local development.
- A seed script / endpoint-free seed (`dotnet run -- seed`) with ~8 realistic schemes
  across all statuses, so reviewers don't open an empty app. Not exposed over HTTP.
